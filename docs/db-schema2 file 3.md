## 1. Database Overview

### 1.1 Database Philosophy

This schema is designed for a **single-vendor juice subscription and delivery SaaS** targeting small operational scale (~20 customers, ~30 deliveries/day). The design prioritises:

- **Financial correctness over performance:** The wallet ledger is strictly append-only. No mutable balance columns exist outside the ledger's own `running_balance_paise` optimisation column.
- **Audit completeness over simplicity:** Every admin mutation is captured in `admin_audit_log` with full JSONB before/after snapshots.
- **Idempotent scheduler safety:** All scheduled jobs are keyed against `scheduler_job_log` to prevent duplicate execution and enable safe reruns.
- **State-machine safety:** Order and subscription state transitions are constrained semantically at the application layer (service classes), not via database CHECK constraints, to preserve flexibility for future transitions while keeping the schema stable.

### 1.2 Transactional Rules

- All financial operations (delivery confirmation + wallet debit, historical correction + ledger insert) are performed inside a **single ACID transaction**.
- Notification dispatch **never** participates in financial transactions. Notifications are sent after transaction commit and their failure never rolls back database state.
- Scheduler job idempotency is enforced via the `scheduler_job_log` table — only one `RUNNING` execution per `(job_name, job_date)` is permitted at a time.
- Row-level locking (`SELECT ... FOR UPDATE`) is used on the `wallet_ledger` table to compute the current running balance before inserting a new ledger entry.

### 1.3 Naming Conventions

- **Tables:** `snake_case` plural nouns (e.g., `users`, `subscriptions`, `wallet_ledger`, `delivery_records`).
- **Columns:** `snake_case` (e.g., `created_at`, `unit_price_paise`, `is_available`).
- **Enums:** PostgreSQL native enum types, named `snake_case` matching their domain (e.g., `subscription_status`, `order_status`). See Section 2.
- **Foreign keys:** Named `fk_<child_table>_<referenced_table>` (e.g., `fk_subscriptions_users`).
- **Indexes:** Named `idx_<table>_<columns>` (e.g., `idx_orders_delivery_date_status`).
- **Unique constraints:** Named `uq_<table>_<columns>` (e.g., `uq_delivery_addresses_customer_id`).

### 1.4 Timestamp Conventions

- All timestamp columns use `TIMESTAMPTZ` (timestamp with time zone) in PostgreSQL.
- The application layer operates exclusively in **Asia/Kolkata (IST, UTC+5:30)** for all business logic, cutoff calculations, and scheduler operations.
- `created_at` columns default to `NOW()` (PostgreSQL server time) and are **immutable after insert**.
- `updated_at` columns are updated by the application layer on every mutation (Spring JPA `@PreUpdate`). They do not use database triggers.
- All `LocalDate` fields (delivery dates, holiday dates, job dates) are stored as `DATE` in PostgreSQL with no timezone component. The application layer is solely responsible for interpreting these relative to IST.

### 1.5 UUID Conventions

- All primary keys are `UUID` type, generated by the application layer using `UUID.randomUUID()` (Java) before insert.
- PostgreSQL `uuid` column type is used (native 16-byte storage).
- JPA entities use `@GeneratedValue(strategy = GenerationType.AUTO)` with `@UuidGenerator` (Hibernate 6+) or an equivalent UUID generation strategy.
- No auto-increment integer PKs are used anywhere.

### 1.6 Soft Delete Philosophy

The following entities are **never hard deleted** and are instead soft-deleted via status fields:

- `users` — `is_active = false` (admin deactivation). Never deleted.
- `subscriptions` — `status = 'CANCELLED'` (terminal state). Never deleted.
- `orders` — `status = 'CANCELLED'` or `'SKIPPED'` for invalidated/skipped orders. Never deleted.
- `products` — `is_available = false`. Never deleted.
- `wallet_ledger` — Rows are immutable and append-only. Never updated or deleted.
- `admin_audit_log` — Immutable. Never deleted.
- `delivery_records` — Never deleted; even for CANCELLED orders that arrive post-lock, the record's status transitions to CANCELLED rather than the row being removed.

The **only entity that supports hard deletion** in MVP is `business_holidays` (see BR-GEN-01).

### 1.7 Money Handling Philosophy

- All monetary values are stored as **`BIGINT` in paise** (1 INR = 100 paise). Example: ₹25.00 = `2500`.
- **Floating-point types (`FLOAT`, `DOUBLE`, `NUMERIC/DECIMAL`) are strictly forbidden for all monetary columns.**
- `amount_paise`, `unit_price_paise`, `total_amount_paise`, `price_per_unit_paise`, `running_balance_paise`, `old_price_paise`, `new_price_paise` are all `BIGINT NOT NULL`.
- The `running_balance_paise` in `wallet_ledger` is a **performance-optimisation derived column**, computed at insert time from the previous row's running balance. The true source of financial truth is always the full ledger history. If `running_balance_paise` is ever found inconsistent, it can be recomputed from scratch.
- Balance direction rules:
  - `CREDIT`, `REFUND`, `ADJUSTMENT` entry types **increase** the running balance.
  - `DEBIT` entry types **decrease** the running balance.
- The `amount_paise` column is always stored as a **positive integer**. Direction is encoded by `entry_type`, not by sign.

## 2. Enum Definitions

All enums are defined as **PostgreSQL native enum types** using `CREATE TYPE ... AS ENUM (...)`. Spring Boot maps these using `@Enumerated(EnumType.STRING)` on JPA entities, combined with appropriate Hibernate dialect configuration for PostgreSQL enums.

> **Flyway note:** PostgreSQL enum types must be defined in migrations before the tables that reference them. All enum `CREATE TYPE` statements appear in `V1__create_enums.sql`.

### 2.3 `subscription_status`

```sql
CREATE TYPE subscription_status AS ENUM ('PENDING_START', 'ACTIVE', 'PAUSED', 'CANCELLED');
```

| Value | Business Purpose |
|---|---|
| `PENDING_START` | Subscription created; effective start date not yet reached. No orders generated. |
| `ACTIVE` | Generating orders daily. Transitioned from `PENDING_START` by `OrderGenerationJob`. |
| `PAUSED` | No new orders generated. Existing `LOCKED` orders remain unchanged and fulfillable. |
| `CANCELLED` | **Terminal state.** No reactivation possible. No new orders ever. |

**Allowed transitions:**
- `PENDING_START` → `ACTIVE` (scheduler-driven only, never event-driven)
- `PENDING_START` → `CANCELLED`
- `PENDING_START` → `PAUSED`
- `ACTIVE` → `PAUSED`
- `ACTIVE` → `CANCELLED`
- `PAUSED` → `ACTIVE`
- `PAUSED` → `CANCELLED`

### 2.8 `order_status`

```sql
CREATE TYPE order_status AS ENUM ('SCHEDULED', 'LOCKED', 'DELIVERED', 'SKIPPED', 'CANCELLED');
```

| Value | Business Purpose |
|---|---|
| `SCHEDULED` | Generated by `OrderGenerationJob`. Awaiting delivery. Subscription still modifiable before cutoff. |
| `LOCKED` | Frozen by `OrderFreezeJob` at 22:00 IST. Customer cannot modify. Admin can override. A `delivery_record` row is created at this point. |
| `DELIVERED` | Delivery confirmed by admin. Wallet debited in the same transaction. |
| `SKIPPED` | Delivery-day operational skip (customer unavailable, product damaged, operational issue). No wallet deduction. |
| `CANCELLED` | Pre-delivery business invalidation (subscription paused, subscription cancelled, product disabled, insufficient balance). No wallet deduction. **Orders cancelled before reaching `LOCKED` state never create `delivery_record` rows. If a previously `LOCKED` order is historically corrected to `CANCELLED`, the existing `delivery_record` row is retained and transitions to `CANCELLED`.** |

### 2.11 `wallet_entry_type`

```sql

```

| Value | Business Purpose | Balance Effect |
|---|---|---|
| `CREDIT` | admin credit; positive balance adjustment | Increases balance |
| `DEBIT` | delivery deduction; manual debit; negative balance adjustment | Decreases balance |

### 2.12 `wallet_source_type`

```sql
CREATE TYPE wallet_source_type AS ENUM (
    'ADMIN_CREDIT',
    'DELIVERY_DEBIT',
    'REFUND',
    'MANUAL_DEBIT',
    'MANUAL_ADJUSTMENT',
    'HISTORICAL_CORRECTION',
    'SYSTEM_ADJUSTMENT'
);
```

| Value | Business Purpose | `created_by_user_id` |
|---|---|---|
| `ADMIN_CREDIT` | Manual wallet top-up by admin after external customer payment. | Admin ID |
| `DELIVERY_DEBIT` | Automatic deduction when admin marks an order `DELIVERED`. | Admin ID (who confirmed delivery) |
| `REFUND` | Admin-issued reversal of a deduction. | Admin ID |
| `MANUAL_DEBIT` | Admin-issued manual deduction. | Admin ID |
| `MANUAL_ADJUSTMENT` | Admin correction for reconciliation. | Admin ID |
| `HISTORICAL_CORRECTION` | Ledger entry created as part of a historical order correction (e.g. `DELIVERED → SKIPPED` with `isSystemError=true`). | Admin ID |
| `SYSTEM_ADJUSTMENT` | System-generated entry (e.g. admin sets wallet balance directly). | `NULL` |

**Notes:**
- `MANUAL_ADJUSTMENT` and `SYSTEM_ADJUSTMENT` do not determine balance direction.
- Balance direction is determined exclusively by `wallet_entry_type`:
    - `CREDIT` increases balance
    - `DEBIT` decreases balance
    - `REFUND` increases balance

### 2.13 `scheduler_job_status`

```sql
CREATE TYPE scheduler_job_status AS ENUM ('RUNNING', 'COMPLETED', 'FAILED');
```

| Value | Business Purpose |
|---|---|
| `RUNNING` | Job has started; not yet complete. Used to detect concurrent/abandoned executions. |
| `COMPLETED` | Job finished successfully. |
| `FAILED` | Job encountered an unrecoverable error. Error details in `error_message`. |

**Rerun rule:** If a `scheduler_job_log` entry exists for `(job_name, job_date)`:
- `RUNNING` → rerun **must be rejected** (concurrent guard).
- `COMPLETED` or `FAILED` → rerun is **allowed** (recovery or manual retry).

## 3. Table Definitions

### 3.1 `users`

Stores all user accounts (both admin and customers) in a single table, distinguished by `role`.

```sql
CREATE TABLE users (
    id                   UUID          NOT NULL DEFAULT gen_random_uuid(),
    name                 VARCHAR(100)  NOT NULL,
    email                VARCHAR(150)  NULL,
    phone                VARCHAR(15)   NULL,
    role                 user_role     NOT NULL,
    auth_provider        auth_provider NOT NULL,
    google_id            VARCHAR(255)  NULL,
    phone_verified       BOOLEAN       NOT NULL DEFAULT FALSE,
    email_verified       BOOLEAN       NOT NULL DEFAULT FALSE,
    is_active            BOOLEAN       NOT NULL DEFAULT TRUE,
    onboarding_completed BOOLEAN       NOT NULL DEFAULT FALSE,
    created_at           TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    updated_at           TIMESTAMPTZ   NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_users PRIMARY KEY (id),
    CONSTRAINT uq_users_google_id UNIQUE (google_id),
    CONSTRAINT uq_users_phone UNIQUE (phone),
    CONSTRAINT chk_users_google_auth CHECK (
        (auth_provider = 'GOOGLE' AND google_id IS NOT NULL) OR
        (auth_provider = 'ADMIN_PASSWORD' AND google_id IS NULL)
    )
);
```

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `UUID` | NOT NULL | `gen_random_uuid()` | Primary key. Application-generated UUID. |
| `name` | `VARCHAR(100)` | NOT NULL | — | Display name. Populated from Google profile for customers. |
| `email` | `VARCHAR(150)` | NULL | — | Email address. From Google profile for customers. May be null if Google does not return email. |
| `phone` | `VARCHAR(15)` | NULL | — | Phone number. Not required at initial Google login. Required to complete onboarding. Unique across all users. |
| `role` | `user_role` | NOT NULL | — | `ADMIN` or `CUSTOMER`. |
| `auth_provider` | `auth_provider` | NOT NULL | — | `GOOGLE` for customers, `ADMIN_PASSWORD` for admin. |
| `google_id` | `VARCHAR(255)` | NULL | — | Google Subject ID (`sub` claim). Unique. Populated only for Google-authenticated customers. NULL for admin. |
| `phone_verified` | `BOOLEAN` | NOT NULL | `FALSE` | Informational flag set manually by admin. Does NOT affect any operational behavior. |
| `email_verified` | `BOOLEAN` | NOT NULL | `FALSE` | Informational only. |
| `is_active` | `BOOLEAN` | NOT NULL | `TRUE` | When `FALSE`: account is deactivated. All `ACTIVE`/`PENDING_START` subscriptions are paused. Login is rejected with 403. |
| `onboarding_completed` | `BOOLEAN` | NOT NULL | `FALSE` | Set to `TRUE` after phone number and delivery address are provided. Controls access to customer business APIs. |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | `NOW()` | **Immutable after insert.** |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL | `NOW()` | Updated by application layer on every mutation. |

**Constraints:**
- `uq_users_google_id`: Unique on `google_id` (nullable unique — NULL values are not considered duplicates in PostgreSQL).
- `uq_users_phone`: Unique on `phone` (nullable unique).
- `chk_users_google_auth`: Enforces that `GOOGLE` auth provider always has a `google_id`, and `ADMIN_PASSWORD` never does.

**Notes:**
- Admin password hash is **not stored in this table**. See `admin_credentials` (Section 3.2).
- Only one admin record exists in MVP. No admin management APIs are exposed.
- Soft delete only: `is_active = false`. Hard deletion is never performed (BR-ACC-03, BR-GEN-01).

### 3.2 `admin_credentials`

Stores the bcrypt-hashed password for the admin account. Separated from `users` for security isolation.

```sql
CREATE TABLE admin_credentials (
    id            UUID         NOT NULL DEFAULT gen_random_uuid(),
    user_id       UUID         NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_admin_credentials PRIMARY KEY (id),
    CONSTRAINT uq_admin_credentials_user_id UNIQUE (user_id),
    CONSTRAINT fk_admin_credentials_users
        FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE RESTRICT
);
```

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | Primary key. |
| `user_id` | `UUID` | NOT NULL | FK → `users.id`. Unique — one record per admin. |
| `password_hash` | `VARCHAR(255)` | NOT NULL | bcrypt hash of admin password. |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | **Immutable after insert.** |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL | Updated on password change. |

**Notes:**
- One-to-one with `users` where `role = 'ADMIN'`.
- Admin password reset is operational (manual DB update). No self-service password recovery in MVP.

### 3.3 `refresh_tokens`

Stores hashed refresh tokens for JWT session management. New login revokes previous token.

```sql
CREATE TABLE refresh_tokens (
    id         UUID         NOT NULL DEFAULT gen_random_uuid(),
    user_id    UUID         NOT NULL,
    token_hash VARCHAR(255) NOT NULL,
    expires_at TIMESTAMPTZ  NOT NULL,
    revoked    BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ  NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_refresh_tokens PRIMARY KEY (id),
    CONSTRAINT fk_refresh_tokens_users
        FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | Primary key. |
| `user_id` | `UUID` | NOT NULL | FK → `users.id`. Multiple rows per user are allowed (history), but only the newest non-revoked row is active. |
| `token_hash` | `VARCHAR(255)` | NOT NULL | SHA-256 or bcrypt hash of the refresh token value. Never store plaintext. |
| `expires_at` | `TIMESTAMPTZ` | NOT NULL | Expiry timestamp. Token is invalid after this time regardless of `revoked` flag. |
| `revoked` | `BOOLEAN` | NOT NULL | `FALSE` by default. Set to `TRUE` on new login (BR-AUTH-04). |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | **Immutable after insert.** |

**Notes:**
- On new customer login, the application sets `revoked = TRUE` on all existing refresh tokens for that `user_id` before issuing the new token (BR-AUTH-04).
- Token refresh validation checks: token hash match AND `revoked = FALSE` AND `expires_at > NOW()`.
- `ON DELETE CASCADE`: if a user is ever hard deleted (which should not happen in MVP), associated tokens are removed.


| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | Primary key. |
| `customer_id` | `UUID` | NOT NULL | FK → `users.id`. **UNIQUE** — enforces one address per customer. |
| `line1` | `VARCHAR(255)` | NOT NULL | Street address line 1. Mandatory. |
| `line2` | `VARCHAR(255)` | NULL | Optional apartment / building detail. |
| `city` | `VARCHAR(100)` | NOT NULL | City name. Mandatory. |
| `state` | `VARCHAR(100)` | NOT NULL | State name. Mandatory. |
| `pincode` | `VARCHAR(10)` | NOT NULL | Postal code. Mandatory. |
| `delivery_notes` | `TEXT` | NULL | Optional delivery instructions (e.g. "Leave at gate"). |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | Set on first address save. **Immutable after insert.** |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL | Updated on every address update. |

**Notes:**
- Address updates use an **UPSERT** pattern (`INSERT ... ON CONFLICT (customer_id) DO UPDATE`), or a plain `UPDATE` since the record always exists after onboarding completion.
- Address changes **bypass the cutoff rule** — they apply immediately (BR-ONB-03, BR-CUT-05).
- Address changes do **not** modify existing orders — address is snapshotted at order generation time (BR-ONB-04).


| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | Primary key. |
| `name` | `VARCHAR(100)` | NOT NULL | Product display name. |
| `description` | `TEXT` | NULL | Optional detailed description. |
| `price_per_unit_paise` | `BIGINT` | NOT NULL | Current price in paise. Used for all future order generation. No locked subscription pricing. |

- Price changes trigger an insert into `product_price_history` in the same transaction.

### 3.6 `product_price_history`

Append-only audit log of every product price change. **Insert-only. Never updated or deleted.**

```sql
CREATE TABLE product_price_history (
    id              UUID        NOT NULL DEFAULT gen_random_uuid(),
    product_id      UUID        NOT NULL,
```

```sql
        )
```

**Idempotency unique constraint:**
```sql
CREATE UNIQUE INDEX uq_wallet_ledger_order_source
    ON wallet_ledger (order_id, source_type)
    WHERE order_id IS NOT NULL;
```

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | Primary key. |
| `customer_id` | `UUID` | NOT NULL | FK → `users.id`. |
| `order_id` | `UUID` | NULL | FK → `orders.id`. Populated for `DELIVERY_DEBIT` and order-linked `HISTORICAL_CORRECTION` entries. `NULL` for admin credits, adjustments, and system entries. |
| `entry_type` | `wallet_entry_type` | NOT NULL | `CREDIT`, `DEBIT`, `REFUND`, or `ADJUSTMENT`. |
| `source_type` | `wallet_source_type` | NOT NULL | Operational origin of the entry. |
| `amount_paise` | `BIGINT` | NOT NULL | Always a **positive integer**. Direction encoded by `entry_type`. |
| `running_balance_paise` | `BIGINT` | NOT NULL | Running balance after this entry. Computed at insert time by reading the previous row's `running_balance_paise` (or 0 if first row). **Performance optimisation — derived from full ledger history.** |
| `description` | `TEXT` | NULL | Human-readable description (e.g. `"Delivery on 2025-07-15 — Orange Juice x2"`). |
| `reference` | `VARCHAR(100)` | NULL | External reference (e.g. UPI ref, cash receipt number). |
| `created_by_user_id` | `UUID` | NULL | FK → `users.id`. Admin ID for manual operations; admin ID who marked `DELIVERED`; `NULL` for `SYSTEM_ADJUSTMENT`. |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | **Immutable after insert.** |

**Idempotency:**
The partial unique index `uq_wallet_ledger_order_source` on `(order_id, source_type) WHERE order_id IS NOT NULL` prevents double deductions for the same order (e.g. `DELIVERY_DEBIT` cannot be inserted twice for the same order).

**Balance Computation Rules:**
- `CREDIT`, `REFUND`, `ADJUSTMENT` entries: `running_balance = prev_running_balance + amount_paise`
- `DEBIT` entries: `running_balance = prev_running_balance - amount_paise`
- Historical correction (`DELIVERED → SKIPPED` with `isSystemError=true`): a `REFUND` entry is inserted (balance increases).
- Historical correction (`SKIPPED → DELIVERED`): a `DEBIT` entry with `source_type = DELIVERY_DEBIT` is inserted. Negative balance is permitted for this case only (BR-HIS-03).

Latest wallet balance resolution must always use:

```sql
ORDER BY created_at DESC, id DESC
```

to avoid same-timestamp ordering ambiguity.

| `target_id` | `VARCHAR(255)` | NOT NULL | UUID of the affected record, or job name for scheduler reruns. `VARCHAR(255)` to accommodate UUIDs and non-UUID identifiers. |
| `old_value` | `JSONB` | NULL | JSON snapshot of the record before the change. `NULL` for creation events or scheduler reruns. |

| `acting_admin` | `UUID` | NOT NULL | FK → `users.id`. Always the admin who performed the action. |

### 3.16 `scheduler_job_log`

Tracks all scheduler job executions. Enforces idempotency per `(job_name, job_date)`.

```sql
CREATE TABLE scheduler_job_log (
    id             UUID                  NOT NULL DEFAULT gen_random_uuid(),
    job_name       VARCHAR(100)          NOT NULL,
    job_date       DATE                  NOT NULL,
    status         scheduler_job_status  NOT NULL DEFAULT 'RUNNING',
    started_at     TIMESTAMPTZ           NOT NULL DEFAULT NOW(),
    finished_at    TIMESTAMPTZ           NULL,
    rows_processed INTEGER               NULL,
    error_message  TEXT                  NULL,
    created_at     TIMESTAMPTZ           NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_scheduler_job_log PRIMARY KEY (id),
    CONSTRAINT uq_scheduler_job_log_name_date UNIQUE (job_name, job_date),
    CONSTRAINT chk_scheduler_job_log_finished
        CHECK (
            (status IN ('COMPLETED', 'FAILED') AND finished_at IS NOT NULL) OR
            (status = 'RUNNING' AND finished_at IS NULL)
        )
);
```

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | Primary key. |
| `job_name` | `VARCHAR(100)` | NOT NULL | Job identifier: `OrderGenerationJob`, `OrderFreezeJob`, `DeliverySheetGenerationJob`. |
| `job_date` | `DATE` | NOT NULL | Operational target date for the job run. Distinct from `started_at`. |
| `status` | `scheduler_job_status` | NOT NULL | `RUNNING` on insert; updated to `COMPLETED` or `FAILED` on finish. |
| `started_at` | `TIMESTAMPTZ` | NOT NULL | Timestamp when job execution began. |
| `finished_at` | `TIMESTAMPTZ` | NULL | Timestamp when job completed or failed. `NULL` while `RUNNING`. |
| `rows_processed` | `INTEGER` | NULL | Number of orders/subscriptions processed. Populated on `COMPLETED`. |
| `error_message` | `TEXT` | NULL | Error details on `FAILED`. `NULL` on `COMPLETED`. |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | **Immutable after insert.** Same as `started_at` in practice. |

**Idempotency Logic (Application Layer):**
1. On job start: attempt `INSERT INTO scheduler_job_log (job_name, job_date, status) VALUES (..., ..., 'RUNNING')`.
2. If insert fails due to `uq_scheduler_job_log_name_date`:
   - Check existing row's `status`.
   - If `RUNNING`: **reject the run** (concurrent execution guard).
   - If `COMPLETED` or `FAILED`: **delete the old row and insert new** to allow rerun.
3. On job completion: `UPDATE scheduler_job_log SET status = 'COMPLETED', finished_at = NOW(), rows_processed = ? WHERE id = ?`.
4. On job failure: `UPDATE scheduler_job_log SET status = 'FAILED', finished_at = NOW(), error_message = ? WHERE id = ?`.

**Notes:**
- `job_date` is the **operational target date**, not the run date. A missed job from the previous day has `job_date = yesterday` even when rerun today (BR-SCH-04).
- On application startup, the scheduler checks the previous 3 calendar days for missing/failed job entries and reruns them in chronological and sequence order (BR-SCH-04).

### 5.3 Ownership Semantics

- **Customer owns:** subscriptions, orders, delivery address, wallet ledger. Customers can only access their own data (BR-ACC-04).
- **Admin owns:** product catalogue, holidays, audit logs. Admin can read and modify all customer data.
- **Scheduler owns:** order creation (via `OrderGenerationJob`), order locking and delivery record creation (via `OrderFreezeJob`), delivery sheet snapshots (via `DeliverySheetGenerationJob`), subscription activation (`PENDING_START → ACTIVE`), and change request application (`APPROVED → APPLIED`).

### 5.4 Lifecycle Dependencies

- A `subscription` cannot be deleted while it has active `orders`.
- An `order` cannot be deleted while it has an associated `wallet_ledger` entry or `delivery_record`.
- A `product` cannot be deleted while referenced by subscriptions or orders.
- A `user` cannot be deleted while referenced by subscriptions, orders, or ledger entries.
- All `ON DELETE RESTRICT` foreign key constraints enforce these dependencies at the database level.

### 5.5 Historical Preservation

**Immutable forever:**
- `wallet_ledger` rows — never updated or deleted.
- `admin_audit_log` rows — never updated or deleted.
- `product_price_history` rows — never updated or deleted.
- `orders.created_at` — immutable after insert.
- `orders.delivery_*` address snapshot columns — immutable after insert.
- `orders.unit_price_paise` at creation — preserved unless admin explicitly overrides.

**Soft deleted (status change only):**
- `subscriptions` → `status = 'CANCELLED'`
- `orders` → `status = 'CANCELLED'` or `'SKIPPED'`
- `products` → `is_available = false`
- `users` → `is_active = false`

**Hard deleted (only entity that supports it):**
- `business_holidays`

## 6. Transaction & Concurrency Notes

### 6.1 Row-Locking Expectations

**Wallet balance computation before deduction (delivery confirmation):**
```sql
SELECT running_balance_paise
FROM wallet_ledger
WHERE customer_id = :customerId
ORDER BY created_at DESC
LIMIT 1
FOR UPDATE;
```
This row-level lock on the latest ledger row ensures that concurrent delivery confirmations for the same customer cannot both read the same running balance and create an incorrect double-deduction.

**Subscription change request creation (supersedence):**
The application must serialize change request creation per subscription to prevent a race condition where two concurrent requests of the same type both succeed as `APPROVED` without the earlier one being marked `SUPERSEDED`. Use `SELECT ... FOR UPDATE` on the `subscriptions` row when creating change requests (BR-SUB-10).

### 6.2 Idempotency Strategy

| Operation | Idempotency Mechanism |
|---|---|
| Order generation | `UNIQUE(idempotency_key)` on `orders`. Key format: `sub_<id>_<YYYY-MM-DD>`. Duplicate inserts are caught by the constraint. |
| Wallet deduction per order | Partial unique index `uq_wallet_ledger_order_source` on `(order_id, source_type) WHERE order_id IS NOT NULL`. Prevents double deduction for the same order. |
| Scheduler job execution | `UNIQUE(job_name, job_date)` on `scheduler_job_log`. `RUNNING` status blocks concurrent reruns. `COMPLETED`/`FAILED` allows reruns. |
| Delivery sheet generation | `UNIQUE(delivery_date)` on `delivery_sheet_snapshots`. Rerun replaces existing row. |

### 6.3 Scheduler Rerun Behavior

- **`OrderGenerationJob` rerun:** Reevaluates all eligible subscriptions for `job_date`. Order-level idempotency (via `idempotency_key` unique constraint) means already-generated orders are silently skipped. Newly eligible subscriptions (e.g. after admin wallet credit) generate their orders.
- **`OrderFreezeJob` rerun:** Reevaluates all `SCHEDULED` orders for `job_date`. Already-`LOCKED` orders and their existing `delivery_records` are not double-processed. A safe `WHERE status = 'SCHEDULED' AND delivery_date = :date` query ensures idempotency.
- **`DeliverySheetGenerationJob` rerun:** Overwrites the existing `delivery_sheet_snapshots` row for the date (`INSERT ... ON CONFLICT (delivery_date) DO UPDATE`).
- **Missed job recovery on startup:** Checks previous 3 calendar days. For each day, runs missing jobs in order: `OrderGenerationJob` → `OrderFreezeJob` → `DeliverySheetGenerationJob` (BR-SCH-04).

### 6.4 Ledger Consistency

- Wallet balance is **never stored on the `users` table** or any other mutable record.
- The live balance is read from `MAX(created_at)` row's `running_balance_paise` in `wallet_ledger` for the customer.
- `running_balance_paise` is computed at insert time and stored as a performance optimisation. It can be fully recomputed from the ledger history if needed.
- All financial operations (delivery confirmation → debit, historical correction → refund/debit) are atomic single-transaction operations.
- Negative balances are possible only for historical correction debits (`SKIPPED → DELIVERED` corrections). Normal order generation blocks on insufficient balance.

### 6.5 Delivery Confirmation Atomicity

When admin marks an order `DELIVERED`:
1. Begin transaction.
2. `SELECT ... FOR UPDATE` on latest `wallet_ledger` row for the customer.
3. Compute new `running_balance_paise`.
4. `UPDATE orders SET status = 'DELIVERED' WHERE id = :orderId`.
5. `UPDATE delivery_records SET status = 'DELIVERED', delivered_at = NOW() WHERE order_id = :orderId`.
6. `INSERT INTO wallet_ledger (customer_id, order_id, entry_type, source_type, amount_paise, running_balance_paise, ...)`.
7. `INSERT INTO admin_audit_log (...)`.
8. Commit transaction.
9. (Post-commit) Send delivery confirmation email if triggered by admin.

### 6.6 Historical Correction Semantics

| Correction | Ledger Action | Balance Constraint |
|---|---|---|
| `DELIVERED → SKIPPED` with `isSystemError=true` | Insert `REFUND` ledger entry with `source_type = HISTORICAL_CORRECTION` in same transaction | Balance increases; always permitted |
| `DELIVERED → SKIPPED` with `isSystemError=false` | No automatic ledger entry. Separate manual ledger action required (BR-HIS-04) | N/A |
| `SKIPPED → DELIVERED` | Insert `DEBIT` ledger entry with `source_type = DELIVERY_DEBIT` in same transaction | Negative balance permitted for this case only (BR-HIS-03) |
| Any → `CANCELLED` (post-lock correction) | No automatic ledger entry. `delivery_records.status = 'CANCELLED'` | N/A |
| Admin quantity/product override | Recalculate `unit_price_paise` + `total_amount_paise` on `orders` in same transaction | No ledger change |

## 8. PostgreSQL-Specific Notes

### 8.1 Partial Unique Indexes

Two partial unique indexes are critical to this schema and must be created explicitly:

```sql
-- Prevents duplicate live subscriptions for same product+customer
CREATE UNIQUE INDEX uq_subscriptions_active_per_customer_product
    ON subscriptions (customer_id, product_id)
    WHERE status IN ('ACTIVE', 'PAUSED', 'PENDING_START');

-- Prevents double ledger deductions for the same order
CREATE UNIQUE INDEX uq_wallet_ledger_order_source
    ON wallet_ledger (order_id, source_type)
    WHERE order_id IS NOT NULL;
```

PostgreSQL partial indexes are not supported by all JPA annotation systems. These must be defined in Flyway migrations, **not** via JPA `@Table(uniqueConstraints = ...)`. Use `columnDefinition` or a separate `V18__create_indexes.sql` migration.

### 8.2 CHECK Constraints

All `CHECK` constraints are defined at the DDL level (enforced by PostgreSQL). Key constraints:

- `chk_users_google_auth` — ensures `GOOGLE` auth always has `google_id`, `ADMIN_PASSWORD` never does.
- `chk_subscriptions_pause_reason` — ensures `pause_reason` is set iff `status = 'PAUSED'`.
- `chk_orders_skip_reason` — ensures `skip_reason` is set iff `status = 'SKIPPED'`.
- `chk_delivery_records_skip_reason` — same for `delivery_records`.
- `chk_delivery_records_delivered_at` — ensures `delivered_at` is set iff `status = 'DELIVERED'`.
- `chk_products_price_positive` — price must be > 0.
- `chk_orders_quantity_positive` — quantity ≥ 1.
- `chk_wallet_ledger_amount_positive` — amount must be > 0.
- `chk_scheduler_job_log_finished` — `finished_at` must be NULL iff `RUNNING`.

### 8.3 Enum Handling Strategy

PostgreSQL native enums (`CREATE TYPE ... AS ENUM`) are used throughout. Spring Boot / Hibernate mapping:

- JPA entities use `@Enumerated(EnumType.STRING)` on enum fields.
- The Hibernate dialect must be configured for PostgreSQL enum type mapping. With Hibernate 6+, use `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` or the equivalent dialect-specific annotation to map Java enums to PostgreSQL enum types.
- Alternatively, store all enum values as `VARCHAR` columns with `@Enumerated(EnumType.STRING)` and add CHECK constraints in migrations. This approach is simpler for Hibernate compatibility but foregoes PostgreSQL type safety. **Either approach is acceptable; the PostgreSQL native enum approach is preferred for type safety.**
- Adding new values to a PostgreSQL enum requires `ALTER TYPE ... ADD VALUE` and is non-transactional in PostgreSQL. Prefer `VARCHAR` with application-layer validation for enums expected to grow (e.g. `admin_audit_log.action_type` is already `VARCHAR` for this reason).

### 8.4 Timestamp Timezone Recommendations

- Use `TIMESTAMPTZ` (not `TIMESTAMP WITHOUT TIME ZONE`) for all timestamp columns.
- Configure the PostgreSQL session timezone via `SET TIME ZONE 'Asia/Kolkata'` or via the JDBC connection string: `?options=-c%20TimeZone%3DAsia/Kolkata`.
- Spring Boot `application.properties`: `spring.jpa.properties.hibernate.jdbc.time_zone=Asia/Kolkata`.
- All `LocalDate` business-logic dates (delivery dates, holiday dates, effective dates) are stored as `DATE` columns (no timezone). The application is responsible for interpreting these as IST dates.

### 8.5 BIGINT Money Storage Rationale

- `BIGINT` (8-byte signed integer) supports values up to ~9.2 × 10^18. In paise, this is ₹92 trillion — more than sufficient for any foreseeable wallet balance.
- No rounding errors: integer arithmetic is exact, unlike `FLOAT` or `DOUBLE`.
- No `NUMERIC/DECIMAL` usage: while `NUMERIC` is also exact, it is slower than `BIGINT` for arithmetic and unnecessary at this scale.
- All arithmetic (multiplication: `quantity × unit_price_paise = total_amount_paise`) is performed with `BIGINT` in the application layer (Java `long`). No SQL-level arithmetic for financial calculations.

### 8.6 JSONB for Audit and Snapshot Columns

- `admin_audit_log.old_value` and `new_value` are `JSONB` (binary JSON with indexing support).
- `delivery_sheet_snapshots.snapshot_json` is `JSONB`.
- `JSONB` supports GIN indexing for future query needs and is more efficient than `JSON` for storage.
- No GIN indexes are created in MVP (volume is too low to justify), but the column type choice preserves the option.

## 9. Potential Inconsistency Review

### ⚠️ INCONSISTENCY-01: `OrderFreezeJob` vs `OrderGenerationJob` Timing Ambiguity

**Documents involved:** `business-rules12.md` BR-SCH-01, `api-spec19.md` Scheduler Timings Appendix

**Issue:** `BR-SCH-01` lists the schedule as:
- `22:00` → `OrderFreezeJob`
- `22:05` → `OrderGenerationJob`
- `22:10` → `DeliverySheetGenerationJob`

However, the API spec appendix lists:
- `OrderGenerationJob` → `00:05 IST daily`
- `OrderFreezeJob` → `22:00 IST daily`
- `DeliverySheetGenerationJob` → `22:10 IST daily`

The API spec places `OrderGenerationJob` at **00:05 IST** (midnight + 5 minutes), while the business rules place it at **22:05 IST** (10:05 PM).

**Impact on schema:** The `scheduler_job_log` table is not affected — it stores `job_date` (the operational target date) rather than the cron schedule. However, the implementing developer must decide which timing is canonical.
